# 動作

[English](../behavior.md)

このページでは、言語サーバーが従う規則を説明します。受け付ける処理の量、受付済みの処理が続く条件、自動選択の追跡、ホバーが返す結果、キャッシュ、期限、再試行、停止を扱います。操作の方法は[使い方](usage.md)で説明します。

## 受付と実行枠

既定では、すべての文書を合わせて最大2件を同時に実行し、実行・待機の合計8件を受け付けます。同じ文書の複数範囲を続けて指定できます。同じ対象への要求は一つの処理を共有します。タブ翻訳の開始は最大1件とし、範囲翻訳が進められる枠を残します。受付順で実行しますが、タブ用の枠を待つ処理だけは後続の範囲翻訳が追い越せます。

受付済みの範囲に同じ対象のタブ翻訳を追加する場合は処理を共有し、追加の実行枠を使いません。この共有は `provider.document` を設定しておらず、`document_split` が無効な場合の動作です。Anthropic API、OpenAI API、OpenAI互換のプロバイダーでは、範囲翻訳の要求がタブ翻訳より少ない出力トークンを求めるため（[Anthropic API](providers/anthropic.md#送信する内容)、[OpenAI API](providers/openai-api.md#送信する内容)、[OpenAI互換API](providers/openai-compatible.md#送信する内容)の「送信する内容」を参照）、タブが共有するのは範囲翻訳の要求を送るまでです。共有した要求はタブ翻訳の上限で送ります。要求を送った後に追加したタブ翻訳は、別の処理になります。`provider.document` を設定している場合と、[`document_split`](configuration.md#文書を分けて送る) を有効にしている場合は、同じ範囲でもタブ翻訳と範囲翻訳を別の処理として扱います。互いに合流せず、それぞれを受付件数に数え、それぞれが実行枠を使います。

部分に分けて送るタブ翻訳も1つの処理で、実行枠を1つ使い、その中で `document_split.parallel` 個までの部分を同時に送ります。このため翻訳プロバイダーは、ほかの処理の要求に加えて、1つのタブ翻訳からその数の部分の要求を受けることがあります。訳文を開くのは、すべての部分が成功したときだけです。最初に失敗した部分で処理が終わり、ほかの部分の要求をやめます。取り消し、期限切れ、文書の編集、認証の変更、[停止](#停止)で説明する停止のあとは、残りの部分の要求を送りません。

上限は `translation_limits.work` で変更できます。

## 受付済みの処理が続く条件

選択・タブ翻訳コマンドは受付時に応答します。選択の変更・解除、別タブへの移動、エディタによるコマンド応答待ちの取り消しでは、受付済みの処理を取り消しません。個々のホバー応答を取り消したり、その応答待ちが時間切れになったりしても、受付済みのコメント翻訳は継続します。コメントAからBへ移ってもAの実行・待機は残り、あとで各コメントに戻って完成訳を読めます。そのため、通りすがりでもZedがホバー要求を送って受付された場合は、翻訳の利用量を消費します。

原文の文書内を編集する・文書を閉じる・認可を変更する・サーバーを終了する場合は、関連する処理と、位置で引くキャッシュの結果を無効にします。送った内容で引く訳文は残ります。[キャッシュ](#キャッシュ)を参照してください。トークン更新では無効にしません。APIキーを使うプロバイダーでは、キーの保存、置き換え、削除が認可の変更に当たります。プロバイダーのアカウントやキーのメニューを開いて閉じるだけなら翻訳を継続します。

## 自動選択

自動選択が直前の選択と重なり、安定待ちを終えた場合は、直前の処理の自動保持だけを置き換えます。途中の空の選択や翻訳対象外の選択では調整の連続性を切らず、別文書か、重ならない翻訳対象の選択を観測すると切ります。明示依頼や別のホバーが共有する処理は残ります。

コメントのホバーと自動選択を合わせた自動保持の既定上限は3件です。満杯で拒否されたコメントのホバーは保持しません。枠が空いた後に戻るか、選択して手動翻訳してください。自動選択では、満杯の間は最新の未受付候補だけを保持するため、D、Eと選択するとDは翻訳されない場合があります。候補は `selection not yet accepted` と表示し、受付済みの待機件数へ加えません。明示操作が満杯で拒否された場合は、ファイル名・行範囲と、受け付けなかったことを通知します。

選択変更はZedからの範囲要求で観測します。一つのサーバーが最新の候補と調整の連続性を扱い、複数エディタの選択を独立には追跡しません。受付済みの異なる範囲は保持します。コピー目的の文章選択でも自動翻訳が始まる場合があります。バックグラウンド翻訳の失敗から新しい処理を自動送信し直すことはありません。

翻訳と無関係な種別に限定されたCode Action要求では、自動翻訳の選択状態を変更しません。

## ホバーが返す結果

ホバーは、その位置を含む完成訳のうち最も新しい依頼の結果を優先します。新しい処理や失敗によって、読める完成訳を隠しません。完成訳がなければ処理中の範囲に合流し、失敗済みなら範囲ごとのエラーと手動再試行の案内を表示します。選択を解除した後やコード内の手動選択でも、以前の依頼を見つけられます。

## キャッシュ

サーバーは完了した訳文を2つの方法で持ちます。ホバー、CodeLens、タブに表示するための位置で引くキャッシュと、同じ文章を送り直さないための、送った内容で引くキャッシュです。

位置で引くキャッシュは、複数範囲の訳をメモリに保持し、`translation_limits.cache` でサーバー全体の件数・容量を制限します。完了順が逆でも、位置を含む完成訳のうち依頼が最も新しいものを表示します。新しい訳が成功した時点で、その範囲に完全に含まれる古い訳を除きます。上限に達すると、長く使われていない項目から外します。

タブ用の結果はホバー用と分け、元文書ごとに成功結果を最大1件保持し、同じ全体予算に含めます。明示的な翻訳依頼で、その表示先にキャッシュがない場合は、もう一方の表示先にある完全に同じ範囲の完成訳を再利用します。依頼した操作の入力上限は引き続き適用します。タブに開くだけではホバー表示は増えず、同じ範囲をホバー用に明示的に翻訳した場合に再利用します。`provider.document` を設定している場合と、`document_split` を有効にしている場合は、もう一方の表示先にキャッシュした結果を再利用せず、それぞれの設定で、または部分に分けて翻訳します。

原文の編集・閉鎖・アカウント変更・再認証で、位置で引くキャッシュの関連項目を破棄します。コメントのホバーで文章がすでに翻訳先の言語だと判断した位置は、ほかの場所で同じ文章を訳しても、文書が変わるまで何も表示しません。キャッシュから外れたMarkdownの範囲は、ホバーだけでは再翻訳しません。選択するか手動実行してください。コメントはホバーで再翻訳できます。

サーバーは翻訳を送る前に、同じ依頼でできた訳文も探します。同じ依頼とは、文章、プロバイダー、モデル、`effort` のように訳文を左右する設定（`speed` は含みません）、`target_language`、`source_language` が同じで、結果の種類も同じものです。種類は、文章全体の訳文、部分に分けて送った文章の部分の訳文、語とその行に対する単語の説明、自動の依頼が文章をすでに翻訳先の言語だと判断した結果の4つです。見つかった訳文は、文章がどこにあっても依頼を送らずに表示します。ほかの位置でも、ほかの文書でも、文章を変えない編集のあとでも同じです。自動の依頼は訳文を使い、なければ翻訳先の言語だという結果を使います。明示の依頼は常に翻訳するため、訳文だけを使います。DeepL APIとGoogle Cloud Translationでは、意味を調べる短さの選択もほかの文章と同じように訳し、その訳文は残しません。部分に分けて送るタブの翻訳は、部分ごとに探し、見つからない部分だけを送ります。各部分は訳文が完了した時点で残し、そのあと文書全体が失敗しても残ります。分けずに送る文章は、範囲でもタブでも同じように残すため、同じ設定で送るなら、`document_split` を有効にしていても両者で共有します。これらの訳文は、アカウントやAPIキーが変わっても残り、新しいアカウントやキーでも使います。メモリーには `translation_limits.cache` と同じ値の別の上限の中で置き、[`disk_cache`](configuration.md#ディスクキャッシュ) を有効にするとディスクにも置き、起動し直したあとも使います。`disk_cache` を有効にしない限り、ホバーでは文章をディスクに保存しません。タブ表示では完成訳を一時ファイルへ書き込みます。失敗・途中切断・取り消し・期限切れの部分訳は公開せず、残しもしません。保持した範囲の失敗は訳文としてではなく、エラーとして表示します。

コードでは、CodeLensのために、結果も翻訳中の作業も重ならないコメントの残した訳文を、依頼の処理とは別に探します。`translation_limits.input_kib.hover` より長いコメントは、その範囲では訳さないため探しません。同じ文書を探し直すのは、文書、残した訳文、アカウントのどれかが変わったあとと、前に探したときに翻訳中の作業と重なって外したコメントがあったときです。残した訳文だけが変わったときは、前に探したコメントをメモリーだけで探します。1回に見つける訳文は、キャッシュが持てる `translation_limits.cache.entries` 件までです。こうして見つかった訳文は、プロバイダーがそのコメントを訳した場合と同じように位置で引くキャッシュに入ります。ホバーで表示し、削除すると残した訳文も削除し、`translation_limits.cache` の上限に数えます。探している間に結果や翻訳中の作業ができた位置には入れず、キャッシュがいっぱいのときはほかの結果を外してまで入れず、文書の同期が保たれていて、文書、残した訳文、アカウントが探し始めたときと同じ場合にだけ入れます。探すことは依頼ではなく、受付や実行の枠を使わず、`Translating…` も表示しません。翻訳先の言語だという結果は、この方法では探しません。

Zedは、編集のあとも同じ文を表示するCodeLensの行を、その行を作った版のコマンドのまま残します。例えば、上に行を足したあとのコメントの訳文の行です。サーバーは、そうした行のうち、訳文や `Translation failed` の行と `Retry` を、その範囲がそのあとの編集で変わっていなければ、いまの位置の同じ範囲に対して実行します。コードでは、その範囲がいまも1つのコメント全体である必要もあります。コメントの `Translate` は、コメントの始まりの位置だけを追い、いまその位置で始まるコメント全体を訳します。このため、コメントを書き換えたり書き足したり、最後に行を足したりしたあとでも働きます。編集がその範囲の始まりをまたいだとき(`Translate` 以外の行では、範囲に触れたとき)、そこのコメントのまとまりが変わったとき(すぐ上に足したコメントの行がそのコメントと結び付いたときなど)、編集の両側のCRとLFが1つの改行になったとき(LFの直前にCRを入れたときなど)は断られます。行を作ってからの編集を、サーバーが持っている必要もあります。サーバーが持つのは直近の更新512回分で、変更の合計は4,096個までです。それを超える場所を1回で変える更新、文書全体の置き換え、同期が失われること、文書を開き直すことのあとは、それより前の行は断られます。`Translate in tab` は、何を編集したかにかかわらず、いまの文書全体を訳します。文書を開き直したときと、同期が失われたときは断られます。Code Actionは、Zedが毎回取り直すため、いままでどおり作られた版でだけ働きます。ファイルを開いたまま言語サーバーが再起動したときも、Zedはそうした行を、終了したサーバーのものとして残します。その行は、ファイルを閉じて開き直すまで、押しても何も起きません。これはサーバーの側では変えられません。

再試行アクションは完成訳を再利用せず、新しく翻訳するか、すでに処理中の翻訳に合流します。残した訳文も使わず、結果で置き換えます。同じキャッシュ済みのタブ結果を再度開く場合は、一時ファイルが削除されたり保存済みの内容が変更されたりしていなければ再利用します。

1件の削除では、指定した範囲と完全に一致するホバー用の訳文、タブの訳文、失敗の記録、翻訳先と同じ言語という結果をキャッシュから削除し、それらのもとになった残した訳文と、同じ文章が翻訳先の言語だという残した結果も削除します。文書ごとの削除は、その原文の結果をすべて、残した訳文とともに削除します。加えて、文書のいまの本文がいまの設定で送るものの訳文を削除します。文章全体と、タブが部分に分けて送るならその部分、コードではコメントの1つずつです。このため、起動し直したあとも使えます。この2つがディスクの残した訳文を消すのは、`disk_cache` が有効なときだけです。全削除では、確認を開いている間に入った結果も含め、すべての文書の結果と、メモリーとディスクの残した訳文をすべて削除します。`disk_cache` がオフでも削除します。開いている訳文タブと受付済みの翻訳はそのままです。

## 期限

ホバー応答は受信から既定20秒で、キュー待ちを含みます。手動・自動選択の範囲翻訳は既定30秒、タブ翻訳は180秒の実行期限をワーカーへの引き渡し時に設定します。保持したコメント翻訳は `hover_timeout_ms` を使い、引き渡しから既定20秒の実行上限を設けます。ホバー応答の待ち期限とは独立しています。合流では実行時間をリセットせず、長い用途が加わった場合だけ元の開始時刻から上限を延ばします。API呼び出し・認証更新・再試行・ストリーミング受信は実行期限に含みます。保持した処理のキュー待ちは別で、先行する処理数は受付・同時実行の上限で制限します。OAuth・管理操作には別の内部制限があります。

## 自動の再試行

HTTP 200の後に通知される過負荷を含め、明示された一時的なサービスエラーは元の期限内で最大一度だけ再試行します。既定の待機は2秒です。数値の `Retry-After` が120秒以内ならその秒数を使い、それ以外の値では手動再試行に委ねます。取り消し・文書の変更・アカウントの変更で再試行待ちも停止します。APIキーが保存、置き換え、削除されると、待っていた再試行は送りません。接続失敗や途中切断は自動で再送しません。再試行では、同じモデル・`effort`・`speed` を送ります。どの失敗でも、`speed` を外して送り直すことはしません。

## 停止

利用枠の上限・アカウントの制限・設定エラーでは自動翻訳を停止します。原因を解消したら、選択範囲または文書の翻訳を明示実行すると再試行できます。再起動や再接続は不要です。明示した再試行が成功するまで自動翻訳の停止は維持します。停止前に受け付けた待機依頼は新たなHTTPを送らず失敗とし、停止通知はまとめ、各範囲の失敗表示を保持します。APIキーを使うプロバイダーも、請求・キー・モデル・権限のエラーを同じ規則で扱います。[Anthropic API](providers/anthropic.md#エラーと停止)、[OpenAI API](providers/openai-api.md#エラーと停止)、[OpenAI互換API](providers/openai-compatible.md#エラーと停止)の「エラーと停止」を参照してください。部分に分けて送る文書では、部分1つが成功すると、文書全体が失敗しても、明示した翻訳の成功として数えます。
